# Source to Requirements

## Mission
Reverse-engineer a **usable, evidence-backed requirements baseline** from existing source code. The final deliverable is a requirements specification that developers can implement against, testers can validate, and maintainers can use to assess behavior changes. Source investigation, evidence traceability, and classification are indispensable quality controls, not substitutes for the requirements deliverable. Reconstruct the current implemented contract without inventing original stakeholder intent or treating every implementation detail or suspected defect as a normative requirement. Read only; never modify analyzed source unless separately authorized.

## Inputs and defaults
- Target: a module, feature, symbol, or path. **User-specified scope takes precedence**: a module request uses a module boundary; a feature request follows its end-to-end observable behavior across modules as needed; a symbol request starts locally and expands only as necessary. If unspecified, ask for one target rather than scanning an entire monorepo.
- Mode: `standard` by default; `quick` for a narrow behavior, `deep` for complex state, cross-language boundaries, or high-risk behavior.
- Version/build: record repository/commit, module root(s), languages, build target and relevant product/variant when available; record Android version only if applicable. Mark unavailable fields unknown.
- Output: Markdown in conversation by default. Create files only when explicitly requested; do not create three files merely because three templates exist.
- Output language: follow the user's request language unless explicitly overridden; see the output language policy below.

## Output language policy
- Default to the language used in the user's request, regardless of the language of source code, templates, or this skill's instructions.
- An explicit language request or `output_language` setting takes precedence. Supported values: `zh-CN` (Simplified Chinese), `en` (English), and `bilingual` (Chinese-English). If language cannot be determined, default to English.
- Do not generate bilingual output unless explicitly requested. In bilingual mode, provide aligned Chinese and English descriptions under the **same** requirement IDs, evidence references, and confidence classifications; do not generate duplicate independent requirement sets.
- Translate explanatory headings, table labels, requirements, scenarios, and summaries as appropriate. Treat the templates as structural skeletons, not mandatory English wording.
- Preserve identifiers, APIs, symbols, file paths, commands, log messages, literal configuration values, and source quotations exactly as written. Do not translate or alter evidence.
- Keep the technical meaning and coverage consistent across languages; avoid unnecessary duplication outside explicitly requested bilingual mode.

## Procedure
1. **Preflight**: Before source investigation, check target readability, Git availability, and Repo availability when relevant; identify Git/Repo/plain-file workspace and relevant project revisions/dirty paths using only targeted, read-only checks. See [environment preflight](references/environment-preflight.md). Missing Git/Repo must not block file-based analysis; never sync, install, or modify the workspace automatically.
2. **Scope**: Classify the request as module, feature or symbol analysis. State the user-requested behavioral boundary, relevant module root(s), repository/commit, languages, build target, interfaces, assumptions and exclusions. Use [scope and module boundary guide](references/module-boundary.md). Define observable entry and outcome.
   **Git source eligibility**: In each owning Git project, default to tracked files plus untracked files not ignored by Git. Exclude ignored untracked files from automatic discovery, trace expansion and requirement evidence. A tracked file stays eligible even if it matches ignore patterns; explicitly user-selected ignored paths may be inspected as documented exceptions. Apply per project in Repo workspaces; see [environment preflight](references/environment-preflight.md) and [code investigation](references/code-investigation.md).
3. **Discover and inventory contracts**: Identify each independently invocable executable, service, API surface, or other component with its own observable input/output/error contract inside the requested scope; inventory its entry points, modes, outputs, failures, and interaction boundaries. Do not equate file count with components or expand into unrelated dependencies. Search narrowly for symbols, APIs, manifest declarations, flags, tests, config overlays, and entry points. Prefer `rg`, `git grep`, `git log` and focused file reads. Do not dump large trees. See [code-investigation](references/code-investigation.md).
4. **Trace**: Follow callers and callees, branches, permission checks, state mutations, persistence, IPC, callbacks, errors and lifecycle **within the requested behavioral scope**. For feature requests, cross module/process boundaries whenever needed to establish the end-to-end outcome. Apply only relevant [language investigation guidance](references/language-analysis.md) for C, C++, Java or mixed-language boundaries. Distinguish production paths from dead code and tests. For Android-specific modules optionally use [Android guide](references/android-framework.md).
5. **Identify core outcomes and formation contracts**: From the requested scope and verified behavior, identify the primary observable outcome(s), decision(s), state change(s), or artifact(s) that give the analyzed behavior its purpose. Reconstruct how each outcome is produced: input/object, trigger, relevant conditions, operation or decision boundary, result semantics, and success/failure validity. Trace which capabilities produce, constrain, orchestrate, or preserve it. Multiple core outcomes or no provable primary outcome are legitimate; do not invent stakeholder goals, force a single root, or expand beyond scope. See [extraction rules](references/requirement-extraction.md).
   **Mandatory intermediate artifact (internal, not necessarily a document section)**: build a source-linked outcome-formation record for every identifiable core outcome: meaning/unit, inputs and preconditions, start/end or decision boundary, derivation, success/failure/validity, and dependent capabilities. Each field must be evidenced or explicitly unresolved. Do not proceed to capability grouping merely because an outcome is named or its output fields are listed.
   **Outcome dependency/lineage check**: When multiple material outcomes are related, trace the evidenced transformation or decision edges between them, including input populations, filtering/aggregation, validity gates, raw versus derived views, and which downstream outputs consume each view. Do not force a linear pipeline or a diagram where outcomes are independent. Record uncertain edges as gaps rather than inferring data flow from names.
6. **Extract and abstract**: Reconstruct system-level outcomes, independent component contracts, and material inter-component interface contracts at their appropriate levels. An end-to-end requirement must not silently replace an independently observable component requirement; a call chain is not an interface specification. Group implementation branches into independently verifiable behavioral contracts, organized by feature/scenario rather than source file or function. Express each requirement in actor/trigger/precondition/observable outcome terms, retaining necessary parameters, failure behavior and compatibility constraints. Separate externally meaningful requirements from build/deployment facts and internal mechanisms; preserve the latter as supporting technical context where useful. See [extraction rules](references/requirement-extraction.md).
   **Classification and deduplication**: Before assigning final IDs, separate observable functional obligations, independently verifiable nonfunctional constraints, and supporting implementation mechanisms. Give each normative rule one authoritative home; cross-reference related FRs/constraints instead of restating the same rule as an NFR. Allocate stable, sequential FR/NFR IDs only after final grouping and order are settled; ensure first appearances in the normative requirements tables follow their numbering, not investigation order.
7. **Verify and review quality**: Reconcile the investigated-behavior inventory against delivered requirements, interface constraints, supporting technical facts, explicit exclusions, and unresolved gaps. No material investigated behavior may silently disappear during abstraction. For every assertion locate supporting source location, actively seek counterexamples and conflicting paths, and check competing branches, gates, and overrides. Review requirements for clarity, consistency, relevant boundary/failure coverage, testability and traceability; link meaningful acceptance conditions without claiming tests were run. Use [evidence validation](references/evidence-validation.md). Never invent file paths, line numbers, tests, or historical intent.
   **Core-contract gate**: Before delivery, test whether the reader can explain how each identified core outcome arises and what it means from the foundational FR(s) alone, without reading component inventory, orchestration, storage or field listings. If not, revisit the producing code and revise; if evidence is unavailable, surface the specific gap as `UNK` and do not claim complete reconstruction. This gate applies to quick/standard/deep whenever a core outcome is identifiable; it does not require inventing one.
   **Final gates**: Check every material outcome dependency and data population for consistency, reconcile duplicate FR/NFR/interface statements, verify ID order and references, and audit evidence-path eligibility under the Git filtering rule. Do not claim that ignore filtering succeeded merely because output directories were only lightly inspected; distinguish tracked files, eligible untracked files, and explicit ignored-file exceptions where material.
8. **Stop**: Stop when the **user-requested behavior** and material alternatives have been checked, or evidence is exhausted. For a feature request, do not stop at a module boundary that prevents explaining the requested outcome. Mark unvisited paths and unresolved edges; do not expand into unrelated code.
9. **Deliver requirements**: Follow the [output routing guide](references/output-template.md). Lead with a usable reconstructed requirements baseline, defining evidenced core outcome/formation contracts before dependent capabilities when identifiable, organized by feature/scenario, with verifiable acceptance conditions and traceable evidence. When source evidence is available, use [requirements template](templates/requirements.md) as the requirements-table skeleton. If source is unavailable, provide an investigation plan instead of fabricated requirements. Read [call-chain template](templates/call-chain.md) only for nontrivial multi-step/cross-boundary flows or when requested. Read [acceptance scenarios template](templates/test-scenarios.md) only when test coverage, boundary cases, or acceptance criteria are relevant or requested. For deep mode also use the compact matrices in the output routing guide. Highlight unknowns and suggested validation steps.

## Modes and output routing
| Mode | Investigation | Default output |
|---|---|---|
| quick | One narrow flow; critical branches | Compact requirements table with evidence; optional brief flow note |
| standard | Requested module or end-to-end feature behavior, interfaces, configurations and error paths | **Required** requirements table; **conditional** call-chain and acceptance sections |
| deep | Complex state, cross-language/cross-module differences, history where accessible | Requirements table plus branch/state, traceability and scoped coverage matrices; conditional detailed call-chain/test sections |

- Include a call-chain section when the evidence crosses meaningful boundaries (e.g. Binder, callbacks, multiple services) or when the flow is essential to explain behavior. Otherwise omit it.
- Include acceptance scenarios when behavior has meaningful branches, failures, permissions, configuration variants, or the user asks for tests. Do not invent test execution results.
- Keep sections together in one answer/document by default. Split into `requirements.md`, `call-chain.md`, and `test-scenarios.md` **only when the user requests separate artifacts**.
- Expand investigation depth only when evidence demands it. Report partial coverage instead of claiming exhaustive analysis.

## Output constraints
- IDs: `FR-001` observable functional behavior (including guards, rejection, failures/fallbacks, and compatibility paths), `NFR-001` evidence-backed quality/nonfunctional constraints (not generic build flags, library dependencies, or implementation mechanisms), `UNK-001` unresolved questions. Do not assign `BR` merely because source contains a conditional or decision branch.
- Classification: behavior kind is an optional descriptive label within the implemented-behavior table, not a separate requirement ID namespace or mandatory section. Keep inferred intent, defect hypotheses, proposed changes, and evidence conflicts distinct from verified implemented behavior; include these sections only when relevant.
- Source filtering: Git-ignored untracked files are excluded by default at discovery, tracing and evidence validation. Do not use `rg --no-ignore`, `rg -uuu`, or blanket filesystem walks to bypass ignore rules. Record explicit user-selected exceptions; when Git is unavailable, use scoped file analysis without pretending Git filtering was applied.
- Evidence: repository-relative path + symbol + line range when verified. For version-controlled paths, associate evidence with the owning Git project's commit; note relevant uncommitted changes. If line range unavailable, cite symbol and mark `line unverified`.
- Confidence: `confirmed` (directly supported implementation or test evidence within stated scope), `inferred` (reasonable interpretation), `unknown` (insufficient evidence). Static-source confirmation does not imply successful build or device/runtime validation. **Never present inferred requirements as original intent.**
- Negative claims require comprehensive search within explicitly stated scope; otherwise say `not found in inspected paths`.
- Do not mistake code volume, orchestration complexity, or number of entry points for the importance of a requirement. Identify the foundational outcome/decision contract and its formation semantics where evidence permits; make supporting capabilities traceable to it without discarding independent contracts.
- For module scopes containing multiple independently observable components, explicitly cover each component's input, modes/conditions, output and failure semantics, and material interface protocols. Use concise grouped sections or a coverage matrix, not automatic one-function-one-requirement or one-file-one-section expansion.
- Every material requirement should have a verifiable outcome or acceptance condition; group repetitive parameter constraints in a subordinate table when that improves usability. Test cases must distinguish existing tests from proposed tests. No unexecuted tests may be reported as passed.
- Security/permission findings: document observed checks and missing evidence; do not assert exploitability without verification.
